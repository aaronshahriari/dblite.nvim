1. INTRODUCTION						*dblite-introduction*

dblite.nvim lets you write SQL in any buffer, run it, and view paginated
results in a split. It manages named connections (with environment-variable
support for credentials), navigates a history of past results, substitutes
bind parameters, and offers context-aware SQL completion via blink.cmp.

Supported databases: Oracle, SQL Server, SQLite, and Redis (including Valkey
and Dragonfly). On a Redis connection the buffer holds Redis commands instead
of SQL; replies land in the same result grid. See |dblite-redis|.

Queries are executed by a native helper binary (`dblite`) that ships with the
plugin or is downloaded from GitHub Releases. Queries run asynchronously, so
Neovim never blocks while a query is in flight; you can cancel with |CTRL-C|.

==============================================================================
2. REQUIREMENTS						*dblite-requirements*

- Neovim 0.10+ (uses `vim.system`, `vim.uv`).
- The `dblite` native binary. Installed automatically (see
  |dblite-installation|) or built with |:DbliteBuild|.
- Optional: `jq` on PATH for pretty-printed JSON in |dblite-inspect|.
- Optional: blink.cmp for |dblite-completion|.

==============================================================================
3. INSTALLATION						*dblite-installation*

On install, dblite downloads a pre-built native binary from GitHub Releases.
If no binary matches your platform it falls back to building from source
(requires GraalVM `native-image`). If the binary is missing at query time,
run |:DbliteBuild|.

vim.pack (Neovim 0.11+) ~

Register the PackChanged hook BEFORE `vim.pack.add()` so the binary is fetched
on install and update: >lua
	vim.api.nvim_create_autocmd('PackChanged', {
	  callback = function(ev)
	    local name, kind = ev.data.spec.name, ev.data.kind
	    if name == 'dblite' and (kind == 'install' or kind == 'update') then
	      require('dblite.download').download_or_build()
	    end
	  end,
	})

	vim.pack.add({
	  { src = 'https://github.com/aaronshahriari/dblite.nvim' },
	})

	require('dblite').setup()
<
lazy.nvim ~

The plugin ships a `build.lua` that lazy.nvim picks up automatically; no
`build =` key is needed. >lua
	{
	  'aaronshahriari/dblite.nvim',
	  config = function()
	    require('dblite').setup()
	  end,
	}
<
After install you MUST call `require('dblite').setup()` once. Passing a table
of options is optional; see |dblite-config|.

4. QUICK START						*dblite-quickstart*

	1. Add a connection:
	   `:DbliteAddConn oracle://system:oracle@localhost:1521/XEPDB1`
	   For SQLite: `:DbliteAddConn sqlite:///absolute/path.db`

	2. Make it active:
	   `:DbliteUseConn <name>`  (or pick it in the panel, |dblite-panel|)

	3. Open a SQL buffer, type a query, and run it:
	   `:Dblite run`        run the whole buffer
	   `:Dblite run at`     run the statement under the cursor

	4. View results in the dbout split. Page with `L` / `H`,
	   inspect with `gi`, toggle column types with `d`. See |dblite-dbout|.

5. CONNECTIONS						*dblite-connections*

Connections are stored at: >
	~/.local/share/nvim/dblite/connections.json    (chmod 600)
<
Passwords may be stored as `$ENV_VAR` references and are expanded from the
shell environment at query time, so secrets never need to be written to disk.

Commands: |:DbliteAddConn| |:DbliteListConns| |:DbliteUseConn|
|:DbliteEditConn| |:DbliteDeleteConn|. The unified |:Dblite| entry point
mirrors these as `:Dblite conn add|list|use|edit|del|file`. All commands that
take a connection name support tab-completion.

URI formats ~
>
	oracle://user[:password]@host[:port]/service
	sqlserver://user[:password]@host[:port]/database
	sqlite:///absolute/path.db
	redis://[[user][:password]@]host[:port][/db]
	rediss://[[user][:password]@]host[:port][/db]      (TLS)
<
Port defaults to 1521 for Oracle, 1433 for SQL Server and 6379 for Redis when
omitted.
SQL Server connections use `encrypt=true;trustServerCertificate=true` for
broad compatibility with local dev and Azure SQL.

SQLite paths must point to an existing regular file. `:memory:` is unsupported
because each command starts a new process and database connection.

Redis requires only a host: authentication is optional and the database is an
index (default 0) rather than a name. Both a bare password and an ACL
`user:password` pair are accepted. Percent-escapes in a URI's userinfo are
decoded, so `redis://:p%40ss@host` stores the password `p@ss`. Credentials are
passed to the helper binary through the environment rather than embedded in the
URL. `rediss://` validates against the system truststore. See |dblite-redis|.

With no argument, |:DbliteAddConn| first prompts for a URI. Leave it blank for
field-by-field setup; SQLite then asks for the type and database path. URI
setup still prompts for a connection name.

You can also edit the raw JSON directly with `:Dblite conn file`. Saving the
file refreshes the panel and re-prefetches the active connection's schema.

6. CONNECTIONS PANEL					*dblite-panel*

|:DblitePanel| toggles a side panel listing all saved connections. The active
connection is marked with `✓`; switching takes effect immediately for the
next query.

Panel keymaps (configurable via `keymaps.panel`, see |dblite-config|):

	`<CR>`	Activate the connection under the cursor
	`cw`	Edit the connection under the cursor
	`q`	Close the panel

7. RUNNING QUERIES					*dblite-queries*

Set an active connection (|:DbliteUseConn| or the panel), then run:

	`:Dblite run`	   Run the entire buffer as one SQL query.
	`:Dblite run at`   Run the statement under the cursor (treesitter-aware).

The statement under the cursor is highlighted briefly when run; the flash
clears after `flash_timeout` ms (see |dblite-config|).

Trailing semicolons are stripped automatically — write SQL however feels
natural. DML statements (INSERT/UPDATE/DELETE) and COMMIT are supported; for
those, the status line reports the affected row count instead of a result
grid.

Running a query from any tab moves the dbout split to that tab. If the result
window was open in another tab it is closed there first.

`max_rows` caps the number of rows returned (default 10000). Results are
paginated in the dbout buffer at `page_size` rows per page (default 100).

Bulk background exports ~				*dblite-bulk*

`:Dblite run bulk csv|json [path]` (or |:DbliteRunBulk|) runs the query at the
cursor (or the whole buffer) asynchronously, streaming the full result set
straight to a file via the native binary. Both forms accept a range, so
`:'<,'>DbliteRunBulk csv` exports only the selected statement(s) (the selection
is expanded to the whole statement it touches); the `run_bulk` keymap also
fires from visual mode. It ignores `max_rows` and never
buffers the result in the editor, so it handles arbitrarily large exports
(e.g. 50k+ rows) without blocking the session — you can keep running normal
queries while it churns. There is no client-side query timeout, so a bulk
export runs until the database returns.

`:Dblite jobs` (or |:DbliteJobs|) toggles the activity panel, which lists
background exports alongside any running watches — see |dblite-panel-activity|
for its layout and keys.

Finished jobs are recorded to a shared store (default
`stdpath('data')/dblite/jobs.json`), so the panel shows past exports across
restarts and across every Neovim instance on the machine. Configure via
`jobs.history`:
`show` (how many past jobs to display), `max_entries` (how many to keep on
disk), `enabled = false` (in-memory only), or `file` (override the location).
Running jobs are never persisted, so a killed instance leaves no stuck
"running" entry. `jobs.cleanup_delay` only controls how long a finished job
stays in the live list before it is shown from history instead.

Note: bulk export requires a native binary that includes `--to-file` support.
If you installed a pre-built release binary, force a source rebuild with
|:DbliteBuild|! (`:DbliteBuild!` or `:Dblite build force`) to pick it up —
plain |:DbliteBuild| downloads the latest release, which may not include it yet.

Watching a query ~					*dblite-watch*

`:Dblite watch [spec]` (or |:DbliteWatch|) re-runs the statement under the
cursor on an interval until something you are waiting for happens, then
notifies you. It is for the queries you would otherwise sit and re-run by hand
waiting for a row to land.

	`:DbliteWatch`                             open the settings popup
	`:DbliteWatch 30s x50`                     every 30s, at most 50 ticks
	`:DbliteWatch every=2m until=rows>5`       until more than 5 rows return
	`:DbliteWatch 1m for=1h until=STATUS=DONE` every minute for an hour
	`:'<,'>DbliteWatch 10s`                    watch the selected statement(s)
	`:DbliteWatchFile 30s`                     watch the whole buffer
	`:DbliteWatchStop`                         stop every running watch

With no spec the popup opens: a small float whose four settings (`every`,
`until`, `max`, `errors`) are ordinary text, so normal motions and `ciw` work
on them. `<CR>` starts, `q` or `<Esc>` cancels. An invalid value reports the
problem and leaves the popup open rather than starting a broken watch. Set
`watch.prompt = false` to skip it and use the configured defaults.

SPEC							*dblite-watch-spec*

A spec is a space-separated list of `key=value` pairs, with two shorthands: a
bare duration sets the interval, and `xN` sets the tick cap.

	`every=`	Time between ticks — `30s`, `2m`, `1h`, or a bare number
		of seconds. A bare duration in the spec means the same.
	`max=`		Tick cap; `0` means unlimited. `times=` and `xN` are
		aliases.
	`for=`		A wall-clock budget converted into a tick cap by
		dividing by the interval.
	`until=`	What to wait for — see |dblite-watch-conditions|.
	`errors=`	Consecutive failed ticks before the watch gives up;
		`0` means never.

CONDITIONS						*dblite-watch-conditions*

The condition lives in the watch rather than in the SQL, so you do not have to
rewrite the query to poll it.

	`changed`		Result differs from the first tick (the default)
	`rows>5`		Row-count comparison: `>` `>=` `<` `<=` `=` `!=`
	`STATUS=DONE`	Any row whose STATUS column equals DONE
	`NAME~aaron`	Any row whose NAME column contains "aaron"
			(case-insensitive substring)
	`STATUS!=PENDING`	Any row whose STATUS column is not PENDING
	`never`		Never match; just run to the tick cap

Column names are matched case-insensitively, which matters for databases that
return upper-case labels; values are matched exactly. If the result has no such
column you get one warning rather than a watch that silently never fires.

A watch stops on the first match, at its tick cap, after `errors` consecutive
failures, or when you stop it by hand, and notifies either way — naming what
matched: >

	dblite: watch matched — orders.sql:12 · STATUS=DONE (row 3)
<
BEHAVIOUR						*dblite-watch-behaviour*

Ticks are chained, not intervalled: the next run is scheduled when the previous
one finishes, so a query that outlives its interval delays the next tick instead
of stacking a second one on top of it.

The connection name and the bind values are frozen when the watch starts, so
switching the active connection or editing `dblite.binds.json` while a watch is
polling never changes what it runs. Each tick spawns a fresh process, so no
connection is held open between ticks.

Watches are session-local and never persisted — a killed Neovim leaves no ghost
behind, and quitting with watches running warns you first. `watch.max_active`
(default 5) caps how many may run at once, so you cannot quietly accumulate a
dozen forgotten pollers.

The activity panel ~				*dblite-panel-activity*

`:Dblite jobs` (or |:DbliteJobs|) toggles a right-side panel listing everything
dblite has in flight: watches first, then running background exports, with
finished exports folded behind a single line. >

	  dblite

	  ◐ orders.sql:12      7/50 · 6 rows · 24s
	  ◐ queue_depth.sql:4   3/∞ · 112 rows · run
	  ⋯ big_dump.csv          running · ? rows

	  ▸ History (18)
<
A watch line reads tick/cap, row count, and the time until its next tick (or
`run` while a tick is in flight). The panel redraws once a second while anything
is live, so the countdown stays honest.

	`<CR>`	Job: open its output file in a new tab. Watch: show its
		latest result in dbout. History line: fold/unfold.
	`K`	Details of the entry under the cursor; a watch includes its
		full per-tick log.
	`x`	Stop a running watch/job, or remove a finished one.
	`r`	Re-point a job at a moved/renamed output file.
	`<Tab>`	Fold/unfold the finished-exports History section.
	`q`	Close the panel.

Pressing `<CR>` on a watch pushes its latest snapshot into the normal result
window through the usual history ring, so paging, |dblite-inspect|, export and
`[` / `]` history navigation all work on it unchanged.

Keys are configurable via `keymaps.jobs`; panel size and behaviour via the
`jobs` config table, and watch defaults via the `watch` table — see
|dblite-config|.

Loading CSV data ~					*dblite-load*

Write a SQL*Loader-style control block in a buffer and run |:DbliteLoad| (or
`:Dblite load`). dblite parses the block, reads the CSV, and opens a preview
of the generated INSERTs; nothing runs until you commit it: >

	LOAD DATA
	INFILE 'employees.csv'
	INTO TABLE employees
	SKIP 1
	FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
	TRAILING NULLCOLS
	( employee_id, name, department )
<
In the preview buffer press `<CR>` to commit (run the INSERTs through script
mode; results appear as a per-row OK/ERROR log in the dbout) or `q` to cancel.
The preview is editable SQL, so you can tweak it before committing. Keys are
configurable via `keymaps.load`; the window style via `load_view`.

This is an emulation, not real sqlldr (the binary has no Oracle client): a
practical subset of the control syntax is turned into INSERTs. Supported:
`INFILE 'path'` (relative to cwd, ~/$ENV expanded), `INTO TABLE name` with an
optional `APPEND` (default) / `REPLACE` (DELETE first) / `TRUNCATE` mode
(`TRUNCATE` uses DELETE FROM on SQLite),
`SKIP n`, `FIELDS TERMINATED BY 'c'` (also `X'09'` hex, e.g. tab), `(OPTIONALLY)
ENCLOSED BY 'c'` (default `"`), `TRAILING NULLCOLS`, and a `(col, ...)` list.
Values are typed best-effort: numbers unquoted, empty fields become NULL,
everything else is quoted. Dates rely on Oracle's implicit NLS conversion.
Not supported: per-column datatypes/transforms, positional fields, direct
path, and inline `BEGINDATA` (`INFILE *`).

8. REDIS						*dblite-redis*

Redis, Valkey and Dragonfly are reached over `redis://` and `rediss://`. The
protocol is spoken directly, so there is no `redis-cli` dependency and values
containing newlines, spaces or binary survive a round trip intact.

With a Redis connection active, the buffer holds Redis commands instead of
SQL. Everything above the result grid — paging, |dblite-history|,
|dblite-inspect|, export, |dblite-bulk| and |dblite-watch| — works unchanged.
>
	KEYS user:*
	HGETALL user:1042
	ZRANGE leaderboard 0 -1 WITHSCORES
	INFO replication
<
FINDING KEYS						*dblite-redis-keys*

`KEYS <pattern>` is served by a full SCAN cursor loop rather than the real
(server-blocking) KEYS command, so it is safe to run against a live instance.
SCAN may return the same key more than once; the listing de-duplicates.
>
	key                | type   | ttl | size
	-------------------+--------+-----+-----
	user:1042          | hash   |     | 7
	session:a83f-2291  | string | 900 | 1204
	queue:jobs         | list   |     | 4
<
`ttl` is the remaining seconds, blank when the key has no expiry set. `size` is
bytes for a string and the element count for every collection type.

A pattern containing no glob metacharacters (`*`, `?`, `[`) is a key name, not
a search, so it skips SCAN entirely and resolves in a single round trip.
Pasting a full key is O(1) rather than a full keyspace walk.

SCAN itself is passed through untouched if you want the raw cursor semantics.

Note that MATCH does not make a scan cheaper: Redis retrieves every key and
applies the pattern afterwards. A narrow pattern reduces what crosses the wire,
not the work the server does.

REPLY SHAPES						*dblite-redis-shapes*

	HGETALL, CONFIG GET, RESP3 map     field   · value
	ZRANGE .. WITHSCORES, ZPOPMIN/MAX  member  · score (a number)
	LRANGE, SMEMBERS, any array        index   · value
	INFO                               section · field · value
	GET, TTL, any scalar               result
	KEYS                               key · type · ttl · size

Nested replies (XRANGE, CLUSTER SLOTS) keep their structure as JSON within the
cell, ready to expand with |dblite-inspect|.

JSON							*dblite-redis-json*

A value that is a JSON document is tagged `json` in the column types (see
|dblite-column-types|). |dblite-inspect| decodes JSON-inside-a-string
recursively, so nested payloads unwrap into real structure. `JSON.GET` uses the
same path.

A value holding JSONL expands to one row per record, so paging and export
operate on records instead of one oversized cell:
>
	line | value
	-----+------------------
	0    | {"id":1,"k":"a"}
	1    | {"id":2,"k":"b"}
<
WATCHING						*dblite-redis-watch*

SCAN offers no consistency guarantee: a key added or removed during the scan
may or may not appear. Re-running is therefore a genuine check, not a
superstition, and |dblite-watch| automates it.
>
	:Dblite watch every=5s      " on LLEN queue:jobs
	:Dblite watch every=30s     " on INFO replication
<
SCRIPTS							*dblite-redis-script*

In script mode (`:Dblite run script`) each line is one command and lines
beginning with `#` are comments, so a purge or cache-warm routine can live in a
file you commit.

WRITING							*dblite-redis-write*

Write by writing the command, as you would write an UPDATE rather than editing
a result cell:
>
	HSET user:1042 email new@example.com
	EXPIRE session:a83f 3600
	DEL session:expired:a83f
<
Arguments are quoted as in redis-cli: double quotes honour escapes (`\n`,
`\t`, `\xHH`), single quotes are literal. A reply of `+OK` is reported as an
executed statement; any other reply is shown in the grid.

LIMITATIONS						*dblite-redis-limits*

`redis+cluster://` and `redis+sentinel://` are not supported yet.

Bind parameters (|dblite-binds|) are a SQL feature and are disabled on Redis
connections: a colon-namespaced key such as `queue:jobs` is otherwise
indistinguishable from a `:jobs` bind reference.

`:Dblite load` (|dblite-load|) generates INSERT statements and is SQL-only.

SQL completion is likewise suppressed, since there is no catalog to read.

9. RESULT BUFFER (dbout)				*dblite-dbout*

Query output appears in a scratch buffer called the "dbout". Its split
direction and size are controlled by `split_dir` and `split_size`
(see |dblite-config|). Toggle its visibility any time with
|:DbliteToggleOut| or `:Dblite toggle dbout` — an in-flight query keeps
running while hidden.

PLACEMENT						*dblite-dbout-split*

|:DbliteSplit| moves the result window without restarting anything: >

	:DbliteSplit right	" beside the editor
	:DbliteSplit below	" under the editor
	:DbliteSplit left | above | tab
	:DbliteSplit		" report the current placement
<
`right`, `left`, `below` and `above` are the unambiguous names; the older
`vertical` (= right) and `horizontal` (= below) remain accepted.

If dbout is open it moves immediately and re-renders at the new width;
otherwise the placement takes effect the next time it opens. Either way it is
remembered — across toggles and across sessions — together with any size you
resized it to by hand. The sized axis is pinned ('winfixwidth' or
'winfixheight') so opening other windows cannot reclaim it.

`cycle_split` (see |dblite-keymaps|, unmapped by default) flips between a
right-hand and a below split, which is useful when switching between long JSON
values and wide result grids.

The first line is a status line whose sections are configurable via
`style.dbout.sections`. Available items: "history", "pagination",
"query_time", "connection", "binds_file".

Default dbout keymaps (configurable via `keymaps.dbout`, see |dblite-config|):

	`L`		Next page			    *dblite_L*
	`H`		Previous page			    *dblite_H*
	`[`		Previous result in history	    *dblite_[*
	`]`		Next result in history		    *dblite_]*
	`K`		Hover: show the query that produced *dblite_K*
			this result
	`d`		Toggle column type annotations	    *dblite_d*
	`gi`		Inspect current page (untruncated)  *dblite_gi*
	`<leader>l`	Toggle dbout fullscreen		    *dblite_fullscreen*
	`<C-c>`		Cancel the in-flight query	    *dblite_CTRL-C*

`<C-c>` also works from any buffer while a query is running: dblite installs
it globally for the duration of the query and restores your original mapping
when the query finishes.

Fullscreen (`<leader>l`) opens the dbout in a new tab and disables cell
truncation so wide values are fully visible; press it again to close the tab
and return.

==============================================================================
10. RESULT HISTORY					*dblite-history*

Every successful query is saved to a history ring. Navigate past results from
inside the dbout buffer:

	`[`	Previous result in history
	`]`	Next result in history

When more than one entry exists, the status line shows `◀ 2/5 ▶`. Press `K`
to hover the executed SQL (bind parameters already substituted); the float
uses SQL highlighting and dismisses when the cursor moves.

History size is controlled by `max_history` (default 20). Set it to 0 for
unlimited.

==============================================================================
11. COLUMN TYPES					*dblite-column-types*

Press `d` in the dbout buffer to toggle column type annotations. When enabled,
each header shows the database type next to the column name: >
	EMPLOYEE_ID [NUMBER] | FIRST_NAME [VARCHAR2] | HIRE_DATE [DATE]
	--------------------+-----------------------+------------------
<
Show types by default with `show_column_types = true`. The default keymap is
`d`, remappable via `keymaps.dbout.toggle_types`. Annotations use the
|hl-DbliteColumnType| group (links to |hl-Comment| by default); override it
with `vim.api.nvim_set_hl()` or `style.dbout.column_type_hl`. >lua
	require('dblite').setup({
	  show_column_types = true,
	  style = { dbout = { column_type_hl = 'Comment' } },
	})
<
==============================================================================
12. INSPECT						*dblite-inspect*

`gi` (or `:Dblite inspect`) opens the current result page in a scratch window
with no column truncation. Three formats — tab-complete
`:Dblite inspect <Tab>` to pick:

	json	Pretty-printed JSON via `jq` (raw fallback if jq is absent).
	table	Same layout as dbout, widths fit actual content.
	csv	RFC-4180 escaped, ready to paste.

The default format is `inspect_format` (default "json"). The scratch window
opens according to `json_view` (default "tab"; also "vertical",
"horizontal", "float"). Press `q` to close it.

For json, `inspect_expand_json` (default true) decodes cell values that are
themselves JSON strings so they nest cleanly instead of showing one escaped
blob.

==============================================================================
13. BIND PARAMETERS					*dblite-binds*

Bind parameters are referenced in SQL with a leading colon, e.g. `:status`,
`:user_id`. Their values come from a `dblite.binds.json` file in the current
working directory. Open/create it with `:Dblite binds` or `<leader>b`.

File format ~
>
	{
	  "status": "pending",
	  "user_id": 42,
	  "name": "O'Brien",
	  "dt": "~SYSDATE"
	}
<
Values are typed; dblite formats them for SQL automatically:

	JSON number		verbatim	    `42` -> `42`
	String			auto SQL-quoted,    `"O'Brien"` -> `'O''Brien'`
				quotes escaped
	String prefixed `~`	raw SQL (strip ~)   `"~SYSDATE"` -> `SYSDATE`

Nested keys are flattened with dots, so `{ "t2kb": { "date": ... } }` and
`{ "t2kb.date": ... }` both satisfy a `:t2kb.date` bind.

Workflow ~

- Run a query: if all referenced params are present in dblite.binds.json the
  query runs immediately. If any are missing, the file opens so you can add
  them; re-run after saving.
- Edit binds: `<leader>b` or `:Dblite binds` toggles the dblite.binds.json
  window. `:w` saves, `q` closes.
- Values are re-read on every execution, so edits take effect on the next run.

The binds window opens as a vertical split by default; set
`binds_split.style = 'float'` for a centered float. See `binds_split` in
|dblite-config|.

Hover (`K` in a SQL buffer, via `keymaps.editor.hover_bind`) shows the value
of the bind token under the cursor.

Add `"binds_file"` to `style.dbout.sections` to show a `binds` badge in the
status line whenever dblite.binds.json exists in the cwd.

14. AUTOCOMPLETE					*dblite-completion*

dblite ships a blink.cmp source providing context-aware SQL completions. Add
it to your blink config: >lua
	sources = {
	  providers = {
	    dblite = { module = 'dblite.blink', name = 'dblite' },
	  },
	  default = { 'lsp', 'path', 'snippets', 'buffer', 'dblite' },
	}
<
What gets completed ~

	General SQL buffer	    SQL keywords + table names
	After FROM/JOIN/INTO/UPDATE  table names first
	After `table.`		    column names for that table
	After `:`		    dblite.binds.json keys + columns as
				    dotted bind suggestions
	Inside dblite.binds.json    dotted column keys (`orders.id`)

Schema is fetched once per connection switch in the background, so subsequent
completions are instant from cache. The source uses the active connection set
by |:DbliteUseConn|. For SQLite, completion covers tables and views in the
`main` schema.

16. KEYMAPS						*dblite-keymaps*

dblite sets keymaps in several scopes. All are configurable (see
|dblite-config|); set any mapping to "" or false to disable it.

global ~  (active from any buffer/window; all unset by default)

Use global maps for cross-cutting actions you want available everywhere:

  `keymaps.global.run`             run the whole buffer
  `keymaps.global.run_at`          run the statement under the cursor
  `keymaps.global.run_script`      run the buffer as a SQL*Plus script
  `keymaps.global.run_bulk`        background bulk export to a file
  `keymaps.global.toggle_dbout`    show/hide the result window
  `keymaps.global.toggle_panel`    toggle the connections panel
  `keymaps.global.toggle_jobs`     toggle the background-jobs panel
  `keymaps.global.toggle_binds`    toggle dblite.binds.json
  `keymaps.global.inspect`         inspect the current page untruncated
  `keymaps.global.fullscreen`      toggle dbout fullscreen
  `keymaps.global.cycle_split`     flip dbout between right and below
  `keymaps.global.connections`     open the connections JSON file

Editor maps are buffer-local (set only in `filetypes` buffers), so they never
fire in unrelated buffers or windows — no hand-rolled autocmds needed.

dbout buffer ~  (active only inside the result buffer)

	`L`		next page		`keymaps.dbout.next`
	`H`		previous page		`keymaps.dbout.prev`
	`[`		previous history	`keymaps.dbout.history_prev`
	`]`		next history		`keymaps.dbout.history_next`
	`K`		hover query		`keymaps.dbout.hover_query`
	`d`		toggle column types	`keymaps.dbout.toggle_types`
	`gi`		inspect page		`keymaps.dbout.inspect`
	`<C-c>`		cancel query		`keymaps.dbout.cancel`
	(unset)	toggle dbout		`keymaps.dbout.toggle_dbout`
	(unset)	flip split placement	`keymaps.dbout.cycle_split`

editor (SQL buffers) ~  (buffer-local; set on the `filetypes` buffers)

	`<leader>b`	toggle binds window	`keymaps.editor.binds`
	`<leader>l`	toggle dbout fullscreen	`keymaps.editor.fullscreen`
	`K`		hover bind value	`keymaps.editor.hover_bind`

The following editor actions are unbound by default (lhs = ""); set an lhs to
enable them (buffer-local, SQL buffers only):

	`keymaps.editor.cycle_split`	flip dbout between right and below
	`keymaps.editor.run`		run the whole buffer
	`keymaps.editor.run_at`		run the statement under the cursor
	`keymaps.editor.run_script`	run the buffer as a SQL*Plus script
	`keymaps.editor.run_bulk`	background bulk export to a file
	`keymaps.editor.toggle_dbout`	show/hide the result window
	`keymaps.editor.toggle_panel`	toggle the connections panel
	`keymaps.editor.toggle_jobs`	toggle the background-jobs panel
	`keymaps.editor.inspect`	inspect the current page untruncated
	`keymaps.editor.connections`	open the connections JSON file

For anything more custom, use the `on_attach(bufnr)` hook (|dblite-config|) —
it runs once per SQL buffer after the built-in maps, the idiomatic replacement
for hand-rolled FileType/BufWinEnter autocmds. `require('dblite').attach(buf)`
applies the editor maps + on_attach to a buffer on demand.

panel ~  (active inside the connections panel)

	`<CR>`		activate connection	`keymaps.panel.select`
	`cw`		edit connection		`keymaps.panel.edit`
	`q`		close panel		`keymaps.panel.close`
	(unset)	toggle from inside	`keymaps.panel.toggle`

binds ~  (active inside dblite.binds.json)

	(unset)	toggle from inside	`keymaps.binds.toggle`

jobs ~  (active inside the background-jobs panel)

	`<CR>`		open job output file	`keymaps.jobs.open`
	`x`		cancel / delete job	`keymaps.jobs.cancel`
	`q`		close panel		`keymaps.jobs.close`
	(unset)		toggle from inside	`keymaps.jobs.toggle`
			(set to your open key for symmetry)

dblite binds no query-running keys globally by default; enable them via
`keymaps.global`, SQL-only maps via `keymaps.editor`, custom maps via
`on_attach`, or map directly against the |dblite-api|.

18. LUA API						*dblite-api*

All functionality is available programmatically: >lua
	local db = require('dblite')

	db.execute()               -- run the current buffer as a query
	db.execute_at_cursor()     -- run the statement under the cursor
	db.execute_script()        -- run the buffer as a SQL*Plus script
	db.run_async(fmt, path, range) -- background bulk export ('csv'|'json');
	                           --   fmt/path optional (prompts if omitted);
	                           --   range = {line1=,line2=} exports a selection
	db.run_bulk_visual()       -- bulk-export the current visual selection
	db.watch(spec, range)      -- watch the statement at the cursor; spec is a
	                           --   string like '30s x50 until=rows>5' (nil
	                           --   opens the popup). See |dblite-watch|.
	db.watch_file(spec)        -- watch the whole buffer
	db.watch_visual()          -- watch the current visual selection
	db.show_result(res, opts)  -- push a dblite.inline result into dbout;
	                           --   opts = { query =, conn = }
	db.toggle_dbout()          -- show/hide the result window
	db.toggle_fullscreen()     -- toggle dbout fullscreen tab
	db.set_split_dir(dir)      -- move dbout: 'right'|'left'|'below'|
	                           --   'above'|'tab'; see |dblite-dbout-split|
	db.cycle_split()           -- flip dbout between right and below
	db.inspect(format)         -- 'json' | 'table' | 'csv'
	db.export(format, path)    -- write the full result set to a file
	db.load()                  -- load a CSV via a LOAD DATA control block
	db.toggle_binds()          -- toggle the dblite.binds.json window
	db.open_binds()            -- open/focus the binds window (no close)
	db.edit_binds()            -- alias for toggle_binds()
	db.edit_connections_file() -- open connections JSON for editing
	db.toggle_panel()          -- open/close the connections panel
	db.open_panel()            -- open the panel
	db.close_panel()           -- close the panel
	db.is_panel_open()         -- returns true/false
	db.toggle_jobs()           -- open/close the background-jobs panel
	db.open_jobs()             -- open the jobs panel
	db.close_jobs()            -- close the jobs panel
	db.is_jobs_open()          -- returns true/false
	db.hover_bind()            -- hover the bind token under the cursor
	db.pick_connection()       -- open the configured connection picker
	db.get_active_conn()       -- the active connection table, or nil
	db.get_flat_binds()        -- flattened dblite.binds.json as a table
	db.attach(bufnr)           -- apply editor keymaps + on_attach to a buffer
	db.inline(opts, cb)        -- headless query, no UI — see |dblite-inline|
<
Example user keymaps. Prefer `keymaps.editor` or `on_attach` (|dblite-config|)

	local db = require('dblite')

	vim.keymap.set('n', '<leader>dj', db.toggle_jobs,       { desc = 'dblite: jobs' })

19. INLINE QUERIES					*dblite-inline* *db.inline()*

`db.inline()` runs a statement against a named saved connection and hands the
result straight back to Lua. It is the only run path that touches no UI: no
result window, no spinner, no |dblite-history| entry, no jobs panel, no flash
highlight, and the active connection is neither read nor changed. That makes
it safe to call from timers, autocommands, statusline functions and your own
plugins — you decide what to do with the rows. >lua
	require('dblite').inline({
	  conn = 'prod',
	  sql  = 'select expires_at from creds where service = :svc',
	  binds = { svc = 'prod-aws' },
	}, function(err, res)
	  if err then return vim.notify(err, vim.log.levels.ERROR) end
	  vim.notify('creds expire ' .. res.rows[1].EXPIRES_AT)
	end)
<
OPTIONS							*dblite-inline-opts*

	sql		(string, required) the statement to run.
	conn		(string, required) the name of a saved connection, as
			shown by |:DbliteListConns|. Unlike |:DbliteRun| this
			never falls back to the active connection, so an
			inline call always hits the database you named.
	binds		(table) values for `:name` references in `sql`, applied
			exactly as |dblite-binds| does. Missing names are
			returned as an error rather than opening the binds
			editor.
	binds_file	(boolean, default false) also read dblite.binds.json
			from the current directory, underneath `binds`. Off by
			default: that file is a per-cwd editing aid, so an API
			call only sees it when it asks.
	max_rows	(number, default `config.max_rows`) row cap; 0 = no cap.
	script		(boolean) run as a multi-statement script, like
			|:DbliteRunScript|. The result carries `results`,
			`executed`, `failed` and `total` instead of rows.
	timeout		(number) milliseconds before the query is killed.
	null_as_nil	(boolean, default false) decode SQL NULL as `nil`
			instead of |vim.NIL|.
	sync		(boolean) block and return instead of calling back.

RESULT							*dblite-inline-result*

	res.rows	list of rows, each a table keyed by column label —
			`res.rows[1].EMAIL`. This is the binary's own wire
			format, so it costs nothing.
	res.values	the same rows positionally, in column order —
			`res.values[1][2]`. Built on first access only.
	res.columns	column labels, in order.
	res.column_types  database type name per column, in order.
	res.count	number of rows returned.
	res.update_count  rows affected by a DML statement. Set instead of
			rows for INSERT/UPDATE/DELETE; -1 for DDL.
	res.conn	name of the connection the query ran on.
	res.elapsed	seconds the query took.
	res.json	the binary's raw JSON output, unparsed.

Note that duplicate column labels collapse, since rows are JSON objects. Alias
them in the query (`select a.id aid, b.id bid`) when that matters.

ASYNC AND SYNC						*dblite-inline-async*

By default `db.inline()` is asynchronous: it returns the |vim.system()| handle
immediately, and your callback runs later on the main loop, so it may safely
call |vim.notify()|, set buffers or otherwise use the API. Keep the handle to
cancel a query that is taking too long: >lua
	local job = require('dblite').inline({ conn = 'prod', sql = q }, on_done)
	vim.defer_fn(function() job:kill(15) end, 5000)
<
Pass `sync = true` (or omit the callback) to block instead. The call then
returns `res, err` directly, which is what statusline and |expr| functions
need — but a slow query freezes the editor, so pair it with `timeout`: >lua
	local res, err = require('dblite').inline({
	  conn = 'prod', sql = 'select count(*) n from jobs where state = 1',
	  sync = true, timeout = 2000,
	})
	return err and '?' or ('jobs: ' .. res.rows[1].n)
<
ERRORS							*dblite-inline-errors*

Nothing here throws. Every failure — a missing binary, an unknown connection
name, unresolved binds, a SQL error from the database, unparseable output —
arrives as an error string: as the callback's first argument when async, or as
the second return value when sync. `res` is nil whenever `err` is set. >lua
	require('dblite').inline({ conn = 'prod', sql = q }, function(err, res)
	  if err then
	    vim.notify(err, vim.log.levels.WARN)
	    return
	  end
	  ...
	end)
<
